# C# Pulumi Exporter Roadmap

This document is the durable implementation context for improving the Structurizr DSL to C# Pulumi exporter. It is intentionally organized as independent numbered work items so future sessions can request a specific item, for example: "implement roadmap item 14".

Keep this document updated as work is completed. Do not remove conceptual context when marking items done; future sessions should be able to understand the target architecture without re-discovering it from code.

## Target Concept

The exporter should transform a processed Structurizr deployment into a standalone C# Pulumi project.

The generated project must not depend on these core runtime projects/packages:

- `LiveArch.Deployment`
- `LiveArch.Deployment.Azure`
- `LiveArch.Transformers`

The generated project may depend on resource/support projects or future packages that are safe to use from standalone Pulumi code, for example:

- `LiveArch.Resources.Azure`
- small export/runtime helper packages that do not depend on the deployment processor
- user-provided packages/projects explicitly configured in exporter options

Built-in LiveArch behavior should be generated as C# source or moved into safe helper packages. User-provided transformer/converter implementations should not be decompiled or validated by the exporter; generated code may call those types directly and rely on configured references plus compiler/runtime tests.

Unsupported constructs should not block export. The exporter should generate as much code as it can and emit localized escape hatches such as:

```csharp
throw new global::System.NotSupportedException("...");
```

or typed expression helpers when the unsupported construct appears inside an initializer expression. This lets users manually patch only the unsupported generated fragments.

## Dependency Version Concept

Do not use any of these for generated dependency version resolution:

- MSBuild metadata
- MSBuild props
- `Directory.Packages.props`

Default versions should be resolved in memory at export time from currently loaded assemblies by package/assembly name. Exporter configuration may provide package references with or without explicit versions:

- explicit version configured: use it when runtime resolution is not preferred or unavailable;
- no version configured: resolve from loaded assemblies;
- unresolved version: report/generate an appropriate diagnostic/escape hatch depending on context.

Main generated project dependencies and generated test project dependencies should use one shared dependency model and resolver path. Avoid separate "main dependency" and "test dependency" option groups unless a future requirement proves that split necessary.

## Testing Concept

Prefer compile/runtime validation of generated projects over string snapshots.

Regression tests for generated output should live in a dedicated, pre-created test project that already references a known exported project, such as `LiveArch.Order.Deployment`. That exported project may initially contain code generated by an older exporter version.

Useful red/green workflow:

1. write or update a test in a dedicated test project that has a normal project reference to a known exported project;
2. run the test against the currently checked-in generated code and allow/expect it to fail when old generated code lacks the feature;
3. change the exporter;
4. run the exporter to refresh generated project files;
5. build the solution normally;
6. run the pre-authored generated-project tests through Pulumi mocks and verify they pass.

Do not dynamically add project references at runtime for these tests. The references are normal solution artifacts; regeneration only updates referenced project contents.

## Independent Work Items

Each item below should be executable as a separate future session. If an item is completed, move it to **Completed Work Items** and update **Current State Summary**.

### 07. Centralize fallback package defaults

Goal: remove scattered fallback version literals from exporter internals and centralize them in a small default package catalog.

Scope:

- Create a single default dependency catalog for package IDs and fallback versions.
- Route baseline package references such as `Pulumi`, `Pulumi.AzureNative`, `Pulumi.DockerBuild`, `Microsoft.NET.Test.Sdk`, `xunit.v3`, and `xunit.runner.visualstudio` through that catalog.
- Keep runtime loaded-assembly resolution as the preferred source.
- Keep explicit configured versions possible.
- Ensure generated project writers never hard-code package versions.

Validation:

- Build solution.
- Export `LiveArch.Order.Deployment` and verify generated `.csproj` still contains required package references.

### 08. Improve dependency diagnostics

Goal: make unresolved versionless dependencies explicit and user-actionable.

Scope:

- Add diagnostics for package references whose versions cannot be resolved from loaded assemblies and were not configured explicitly.
- Decide whether unresolved dependency versions should fail export immediately or be represented in the generated project with an actionable comment/placeholder.
- Prefer preserving export output where possible.

Validation:

- Add tests for a versionless package that can be resolved.
- Add tests for a versionless package that cannot be resolved.

### 09. Preserve transformer metadata structurally

Goal: stop storing only transformer type names in expression models.

Scope:

- Extend expression model types to capture transformer DSL name, parameter, implementation type, and known/custom classification.
- Update transformer pipeline/processor code so relationship and inline transformers record the structural metadata.
- Preserve enough data for future generated code to render built-in equivalents or custom transformer calls.

Validation:

- Existing transformer behavior remains unchanged at runtime.
- Export model contains structured transformer metadata for dependency mappings and inline pipelines.

### 10. Preserve converter metadata structurally

Goal: record converter data well enough to generate executable code later.

Scope:

Validation:

- Existing converter tests continue passing.
- Export model can distinguish known built-in converters from user-provided converter names.

### 11. Generate built-in transformer equivalents

- Generated code compiles without `LiveArch.Transformers` reference.
